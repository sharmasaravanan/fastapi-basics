A. What is an API?

How two programs talk to each other, using a simulated power-operations example.

The scenario

Imagine a Power Operations Health Monitor. It keeps simulated voltage readings for a few substations. Several people and programs want those readings: an operator's dashboard, a mobile app, a daily report script. Instead of each one reading the data files directly, they all ask the Monitor through one controlled doorway. That doorway is an API.

Simulated data only. The equipment readings here are invented for training. This example does not connect to any real power equipment or network.

Four words to learn first

Client

The program that asks. A web browser, a mobile app, a script, or the curl command.

Server

The program that answers. It runs continuously and waits for requests. In this module the server is our FastAPI application.

API

Application Programming Interface. A published set of rules for how to ask a program for something and what shape the answer will take.

HTTP

The common language of the web that clients and servers use to send requests and responses.

What it isA defined way for one program to request data or actions from another program, without needing to know how that program works inside.
Why it mattersOne system (the Monitor) can serve many different users and tools consistently. Teams can change internals without breaking everyone who depends on the answers.
How it worksThe client sends a request to a specific address. The server reads it, finds or calculates the data, and sends back a response.
ExampleA client asks for /readings/SUB-103 and receives the simulated voltage and status of that substation as JSON.
Common mistakeThinking an API is a website or a database. It is neither. It is the controlled doorway in front of data or logic.

The request-response lifecycle, step by step

  1. The client sends a request. It names a method (GET) and an address (/readings/SUB-103).
  2. The FastAPI application receives it. It matches the address to one of its functions.
  3. The function looks for data. In our example it searches a simple Python list. A real system might query a database.
  4. The data comes back to the function.
  5. FastAPI builds the response: a status code (such as 200) plus a JSON body.
  6. The client receives the response and shows it, stores it or acts on it.

User interface, API and database: three different things

User interface (UI)APIDatabase
Built forHumansOther programsStoring data safely
Looks likeButtons, charts, formsAddresses that return structured data (JSON)Tables or records on disk
Power exampleAn operator's dashboard screenGET /readingsStored history of readings
Who talks to itThe person using the screenThe dashboard, mobile app and scriptsOnly the API (not everyone directly)

Analogy: the screen is the counter, the API is the clerk who takes your request form, and the database is the records room. The clerk has rules about what can be asked and how the answer is written. The analogy helps, but remember the technical point: the API is software that receives structured requests and returns structured responses.

Why applications communicate through APIs

  • One source of truth: every consumer gets the same answer.
  • Safety: the API decides what may be asked. Clients do not touch the database directly.
  • Independence: the dashboard team and the data team can change their own parts separately.
  • Reuse: a browser, a phone app and a script all use the same API.
Check your understanding

A report script wants today's SUB-103 voltage. Which is the client and which is the server?

Answer: the script is the client (it asks). The Monitor's FastAPI application is the server (it answers).

B. What is FastAPI?

A Python framework that turns ordinary Python functions into web API endpoints.

Why Python alone is not enough

A plain Python script starts, does its work and ends. It does not listen on a network port, understand HTTP or keep waiting for visitors. To act as an API, a program must stay running, accept connections, read HTTP text, pick the right code, and write a correctly formatted answer. Doing all that by hand is long and error-prone.

What a web framework does

A web framework is a library that handles the repetitive web work so you only write the useful part. With FastAPI you write a normal function, add one line above it, and FastAPI connects it to an address.

What it isFastAPI is a free, open-source Python framework for building APIs.
Why it mattersIt is small to learn, checks incoming data automatically, and writes interactive documentation for you. It suits lightweight backend services and microservices, which is why it appears often in container training.
How it worksYou decorate functions (@app.get("/health")). When a request arrives for that address, FastAPI calls your function and converts what it returns into a JSON response.
ExampleA 4-line function returning {"status": "running"} becomes a working /health endpoint.
Common mistakeBelieving FastAPI itself is the server that listens on the port. It is not. That job belongs to Uvicorn (below).

Uvicorn: the server that runs FastAPI

What it isUvicorn is a lightweight ASGI server. ASGI is a standard "plug shape" that lets a web server talk to a Python web application.
Why it mattersFastAPI is a framework, not a running server. Without Uvicorn nothing listens on port 8000.
How it worksUvicorn opens the port, accepts connections, hands each request to FastAPI, and sends FastAPI's answer back to the client.
Examplepython -m uvicorn app:app means "run the object named app found in the file app.py".
Common mistakeRunning python app.py and expecting a server. Nothing starts because the file only defines the application.

Two features you get automatically

Validation

You declare what a value must look like using type annotations (for example "text" or "number"), and Pydantic (a data-checking library used by FastAPI) enforces it. Our /alerts endpoint accepts only active or resolved. Anything else gets an automatic 422 response before your code runs.

Interactive documentation

FastAPI writes a web page listing every endpoint and lets you try it. Open /docs on the running server. No extra work is needed.

Common mistake: assuming "microservice" means "small code is enough". A microservice is a small, focused service that does one job and talks to others over APIs, which is exactly the pattern Docker and Kubernetes manage.

C. HTTP fundamentals

The vocabulary every API conversation uses.

What it isHTTP (HyperText Transfer Protocol) is the set of rules for sending a request from a client and getting a response from a server.
Why it mattersEvery API call, browser page, curl command and Kubernetes health check uses it. Reading an HTTP response is the key troubleshooting skill.
How it worksA request states what to do (method), where (URL), and optional extra details (headers, body). The response states how it went (status code) plus headers and a body.
ExampleGET http://127.0.0.1:8000/health returns status 200 and body {"status":"running"}.
Common mistakeLooking only at the body. Always check the status code first. A body can look reasonable even when the call failed.

Anatomy of a request and response: click any part

The same exchange as raw text

GET /readings/SUB-103 HTTP/1.1
Host: 127.0.0.1:8000
Accept: application/json

HTTP/1.1 200 OK
content-type: application/json

{"equipment_id":"SUB-103","name":"West Substation","voltage_kv":205.2,"status":"investigate"}

Anatomy of a URL

http://127.0.0.1:8000/alerts?status=active

  • http:// the scheme: which protocol to speak.
  • 127.0.0.1 the host: which computer. 127.0.0.1 (also localhost) always means "this very computer".
  • :8000 the port: which program on that computer. Think of the host as a building and the port as a room number.
  • /alerts the path, which selects the route.
  • ?status=active the query string: optional filters after a ?.

Key terms with examples

HTTP request

The message the client sends. Example: GET /health.

HTTP response

The message the server returns: status code, headers and usually a body.

Route and endpoint

A route is a path pattern the app recognises, such as /readings/{equipment_id}. An endpoint is the route plus its method, for example GET /readings. People often use the words interchangeably.

Request body

Data the client sends to the server, usually with POST, PUT or PATCH. Our app only reads data, so it needs none.

Response body

The data the server sends back. In our API it is always JSON.

Headers

Labelled details about the message, such as the type of content (content-type: application/json).

HTTP methods

MethodMeaningPower-monitor exampleTypical success code
GETRead data. Changes nothing.Get all readings200
POSTCreate something new.Add a new alert201
PUTReplace an item completely.Replace all settings of SUB-101200
PATCHChange part of an item.Update only the status of an alert200
DELETERemove an item.Delete a resolved alert200 or 204

In this module our app uses only GET. The other methods are listed so you can recognise them. Common mistake: typing a URL into the browser always sends GET, so you cannot test POST that way. Use /docs or curl for that.

JSON

What it isJSON (JavaScript Object Notation) is a plain-text format for structured data that both people and programs can read.
Why it mattersIt is the shared format of nearly all modern APIs, so any language can understand the answer.
How it works{ } holds an object (named values). [ ] holds a list. Names and text are in double quotes. Numbers and true/false are written without quotes. Items are separated by commas.
Example{"equipment_id": "SUB-101", "voltage_kv": 220.1}
Common mistakeUsing single quotes or leaving a trailing comma. Both make the JSON invalid.

Status codes

CodeNameMeaningIn our app
200OKThe request worked.Every successful GET
201CreatedA new item was created.Not used yet (would follow a POST)
400Bad RequestThe request was malformed or unacceptable.Not used by our code
404Not FoundThe address or item does not exist./readings/SUB-999
422Unprocessable ContentThe request was well-formed but the values are invalid./alerts?status=banana
500Internal Server ErrorThe server code crashed unexpectedly.Appears only if a bug exists
  • 2xx = success. 4xx = the caller did something wrong. 5xx = the server has a problem.
  • Analogy: 200 is "here is your file", 404 is "no such file in the records room", 422 is "your form has an invalid entry", 500 is "the clerk fell over". Technically, each code is simply a number the server reports.
  • Some versions of the libraries print 422 as "Unprocessable Entity". Same code, older name.

File 1: app.py

import os
from typing import List, Literal, Optional

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

app = FastAPI(title="Power Operations Health Monitor (Simulated)")


class Reading(BaseModel):
    equipment_id: str
    name: str
    voltage_kv: float
    status: str


class Alert(BaseModel):
    alert_id: str
    equipment_id: str
    message: str
    status: str


# Simulated data only. Nothing here connects to real power equipment.
READINGS = [
    Reading(equipment_id="SUB-101", name="North Substation", voltage_kv=220.1, status="normal"),
    Reading(equipment_id="SUB-102", name="East Substation", voltage_kv=218.7, status="normal"),
    Reading(equipment_id="SUB-103", name="West Substation", voltage_kv=205.2, status="investigate"),
]

ALERTS = [
    Alert(alert_id="ALT-001", equipment_id="SUB-103", message="Voltage below normal range", status="active"),
    Alert(alert_id="ALT-002", equipment_id="SUB-103", message="Voltage trend under review", status="active"),
    Alert(alert_id="ALT-003", equipment_id="SUB-101", message="Routine inspection completed", status="resolved"),
    Alert(alert_id="ALT-004", equipment_id="SUB-102", message="Cooling fan warning cleared", status="resolved"),
]


@app.get("/")
def home():
    return {
        "application": "Power Operations Health Monitor (Simulated)",
        "environment": os.getenv("APP_ENV", "training"),
    }


@app.get("/health")
def health():
    return {"status": "running"}


@app.get("/readings", response_model=List[Reading])
def list_readings():
    return READINGS


@app.get("/readings/{equipment_id}", response_model=Reading)
def get_reading(equipment_id: str):
    for reading in READINGS:
        if reading.equipment_id == equipment_id:
            return reading
    raise HTTPException(status_code=404, detail=f"Equipment {equipment_id} not found")


@app.get("/alerts", response_model=List[Alert])
def list_alerts(status: Optional[Literal["active", "resolved"]] = None):
    if status is None:
        return ALERTS
    return [alert for alert in ALERTS if alert.status == status]

E. Explain the code, piece by piece

Eight small pieces. Each shows the code, what it means, what happens when a client calls it, and the expected response.

The JSON below is formatted over several lines for easy reading. A real API response is usually printed on one line.

1. Imports: bringing in tools
import os
from typing import List, Literal, Optional

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

Plain English: before using a tool you must say where it comes from. os lets us read an environment setting. typing helps describe data shapes. FastAPI is the framework, HTTPException lets us return errors, and BaseModel from Pydantic describes the shape of our data.

When a client calls it: nothing. Imports run once when the server starts.

Expected response: none. If a library is missing you will see ModuleNotFoundError at startup (see Section I).

2. Creating the application
app = FastAPI(title="Power Operations Health Monitor (Simulated)")

Plain English: this creates one FastAPI application and gives it the name app. The title appears at the top of the /docs page.

When a client calls it: nothing directly. But the command uvicorn app:app looks for this exact name: file app, variable app.

Expected response: none. Open /docs to see the title.

3. Type annotations and Pydantic models: describing data
class Reading(BaseModel):
    equipment_id: str
    name: str
    voltage_kv: float
    status: str

Plain English: this is a template for one reading. str means text and float means a number with decimals. The part after the colon is a type annotation: a label saying what kind of value belongs there. FastAPI and Pydantic use the template to check data and to document the response.

When a client calls it: any endpoint that returns a Reading is checked against this template. A reading with a text voltage would be rejected before reaching the client.

Expected response shape:

{
  "equipment_id": "SUB-101",
  "name": "North Substation",
  "voltage_kv": 220.1,
  "status": "normal"
}
4. Lists, dictionaries and JSON
READINGS = [
    Reading(equipment_id="SUB-101", name="North Substation", voltage_kv=220.1, status="normal"),
    Reading(equipment_id="SUB-102", name="East Substation", voltage_kv=218.7, status="normal"),
    Reading(equipment_id="SUB-103", name="West Substation", voltage_kv=205.2, status="investigate"),
]

Plain English: square brackets make a list: an ordered collection. Each item is one Reading. This is our simulated "data source". A dictionary (curly braces with name: value pairs) is similar to a JSON object, and you will see one in the / endpoint below.

When a client calls it: FastAPI automatically converts Python lists, dictionaries and models into JSON. This is called serialization.

Common mistake: restarting the server and expecting changes made earlier to remain. This list lives in memory only, so it resets every start.

5. A route: @app.get and a function
@app.get("/health")
def health():
    return {"status": "running"}

Plain English: the line starting with @ is a decorator: a label attached to the function below it. It says "when a GET request arrives for /health, run this function". def defines the function, and return hands back the answer. The indented lines belong to the function.

When a client calls it: curl http://127.0.0.1:8000/health

Expected response: status 200, body:

{"status": "running"}

The home route GET / works the same way and returns a dictionary with application and environment. The environment comes from os.getenv("APP_ENV", "training"), which means "use the setting named APP_ENV, or training if it is not set".

6. Returning a list with a response model
@app.get("/readings", response_model=List[Reading])
def list_readings():
    return READINGS

Plain English: response_model=List[Reading] promises "the answer is a list of readings". The function simply returns the whole list.

When a client calls it: curl http://127.0.0.1:8000/readings

Expected response: status 200, body is a JSON list:

[
  {"equipment_id": "SUB-101", "name": "North Substation", "voltage_kv": 220.1, "status": "normal"},
  {"equipment_id": "SUB-102", "name": "East Substation", "voltage_kv": 218.7, "status": "normal"},
  {"equipment_id": "SUB-103", "name": "West Substation", "voltage_kv": 205.2, "status": "investigate"}
]
7. Path parameter and HTTPException (404)
@app.get("/readings/{equipment_id}", response_model=Reading)
def get_reading(equipment_id: str):
    for reading in READINGS:
        if reading.equipment_id == equipment_id:
            return reading
    raise HTTPException(status_code=404, detail=f"Equipment {equipment_id} not found")

Plain English: the part in curly braces, {equipment_id}, is a path parameter: a changing piece of the address. Whatever the client puts there is passed to the function. The function looks through the list. If it finds a match it returns it. If it reaches the end without finding one, raise HTTPException stops and sends a 404 with a message.

When a client calls it: curl http://127.0.0.1:8000/readings/SUB-103 finds a match.

{"equipment_id": "SUB-103", "name": "West Substation", "voltage_kv": 205.2, "status": "investigate"}

And curl -i http://127.0.0.1:8000/readings/SUB-999 does not:

{"detail": "Equipment SUB-999 not found"}

Common mistake: IDs are case-sensitive. sub-103 will return 404.

8. Query parameter and filtering
@app.get("/alerts", response_model=List[Alert])
def list_alerts(status: Optional[Literal["active", "resolved"]] = None):
    if status is None:
        return ALERTS
    return [alert for alert in ALERTS if alert.status == status]

Plain English: a function input that is not in the path becomes a query parameter, written after ? in the URL. = None makes it optional. Literal["active", "resolved"] allows only those two words. The last line builds a new list keeping only alerts whose status matches.

Path vs query: a path parameter identifies one thing (/readings/SUB-103). A query parameter narrows or filters a collection (/alerts?status=active).

When a client calls it: curl "http://127.0.0.1:8000/alerts?status=active"

[
  {"alert_id": "ALT-001", "equipment_id": "SUB-103", "message": "Voltage below normal range", "status": "active"},
  {"alert_id": "ALT-002", "equipment_id": "SUB-103", "message": "Voltage trend under review", "status": "active"}
]

With ?status=banana FastAPI answers 422 automatically, without running your function:

{"detail":[{"type":"literal_error","loc":["query","status"],"msg":"Input should be 'active' or 'resolved'","input":"banana","ctx":{"expected":"'active' or 'resolved'"}}]}

G. Call the API

Three ways to talk to your running server.

Before you start: these examples need your local server from Section F to be running. This web page does not run the API. If the server is stopped you will see "connection refused".

Type an address into the browser's address bar and press Enter. The browser sends a GET request.

  • http://127.0.0.1:8000/
  • http://127.0.0.1:8000/health
  • http://127.0.0.1:8000/readings
  • http://127.0.0.1:8000/readings/SUB-103
  • http://127.0.0.1:8000/alerts?status=active

Firefox shows JSON in a tidy viewer. Chrome and Edge show plain text, which is still valid JSON. Limit: a browser address bar can only send GET, and it does not show the status code clearly. For that, use /docs or curl -i.

Open http://127.0.0.1:8000/docs. FastAPI generated this page from your code.

  1. Click an endpoint such as GET /readings/{equipment_id} to expand it.
  2. Click Try it out.
  3. Type a value, for example SUB-103, in the equipment_id box.
  4. Click Execute.
  5. Read the results: the Curl command it used, the Request URL, the Server response with its Code and Response body.

For /alerts, the status box offers the allowed values. Because FastAPI knows the rules, the docs page is always in step with the code. Also available: /redoc (a read-only style) and /openapi.json (the machine-readable description).

curl is a command-line tool that sends HTTP requests. Open a second terminal (the first is busy running the server).

Windows PowerShell note: in older Windows PowerShell, curl is an alias for a different command. Type curl.exe instead of curl if you get odd output. Also use double quotes around any URL containing ?.

curl http://127.0.0.1:8000/health

Add -i to see the status line and headers, which is how you spot a 404:

curl -i http://127.0.0.1:8000/readings/SUB-999

7. Alerts with an invalid value

Method: GET   URL: http://127.0.0.1:8000/alerts?status=banana   Status: 422

curl -i "http://127.0.0.1:8000/alerts?status=banana"
{"detail":[{"type":"literal_error","loc":["query","status"],"msg":"Input should be 'active' or 'resolved'","input":"banana","ctx":{"expected":"'active' or 'resolved'"}}]}

Reading it: loc says the problem is in the query parameter status. msg says what is allowed. 404 means "that thing does not exist"; 422 means "I understood the request but a value is not acceptable".

J. How FastAPI connects to Docker and Kubernetes

A conceptual bridge to the next sessions. You will not write Dockerfiles or Kubernetes YAML here.

The journey: click a stage

Why each idea matters

Why the app runs on a port

A computer can run many network programs. The port number tells incoming traffic which one to talk to. Our API listens on 8000. Containers and Kubernetes use that same number to route traffic to it.

Why 0.0.0.0 inside a container

127.0.0.1 means "only this same machine". Inside a container, that means only the container itself, so traffic arriving from outside is refused. 0.0.0.0 means "accept connections on every network interface", which allows the container's published port to reach the app.

Why port 8000 must match

Docker and Kubernetes forward traffic to a container port. If the app listens on 8000 but the setup forwards to 8080, requests reach nothing and you get "connection refused".

Why Docker packages dependencies

Your laptop has Python and the right packages. A server may not. A Docker image bundles the app, Python and the libraries from requirements.txt, so it behaves the same everywhere.

Why Kubernetes

One container is easy. Dozens across many machines need something to start them, restart failures, scale and give them a stable address. Kubernetes does that.

Local versus container: one setting changes

On your laptop (today)Inside a container (later)
Host setting--host 127.0.0.1--host 0.0.0.0
Port--port 8000--port 8000 (matches the container port)
--reloadUsed for convenienceNot used

Preview only In the container sessions you will see the start command in this form. Do not run it today, and no Dockerfile syntax is needed yet:

python -m uvicorn app:app --host 0.0.0.0 --port 8000

Common mistake: keeping 127.0.0.1 in a container, then wondering why the published port gives "connection refused" even though the container is running.
