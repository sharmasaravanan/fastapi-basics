Why Docker?

"It works on my machine!" is one of the most common sentences in software teams. Docker exists largely to make that sentence unnecessary.

The problem

An engineer builds a small Python service that reports substation equipment readings. It runs perfectly on their laptop. They hand the code to the operations team, and it fails on the server. The code did not change. The environment did.

Different runtime

The laptop has Python 3.12. The server has Python 3.8. Newer syntax simply does not run on the older version.

Different dependencies

The laptop has FastAPI and uvicorn installed. The server has never had pip install run on it, or has other versions.

Different surroundings

Operating system, environment variables, file paths, installed system libraries and open ports all differ between machines.

What is a container?

A container is a normal process on a host machine, started from an image, that is given its own isolated view of files, processes and networking.

The parts, from top to bottom

Container versus virtual machine

A container is NOT a virtual machineA virtual machine includes a complete guest operating system with its own kernel, started on virtualized hardware. A container shares the host's kernel. It is an ordinary process (or small group of processes) that the kernel isolates using features called namespaces (what the process can see) and cgroups (how much CPU and memory it may use).
ContainerVirtual machine
Own kernel?No, shares the host kernelYes, each VM has its own
Typical sizeTens to hundreds of MBOften several GB
Typical start timeUsually a second or lessUsually tens of seconds to minutes
Isolation strengthGood, but weaker boundary than a VMStronger boundary
Best forPackaging and running one applicationRunning a whole separate operating system
Windows and macOSLinux containers need a Linux kernel. Docker Desktop on Windows or macOS quietly runs a small Linux virtual machine and starts your containers inside it. The containers still share that VM's kernel with each other.

Image versus container

An image is a read-only template. A container is a running instance created from it. One image can produce many containers.

Analogies that help

  • Image is to container as installer is to running program.
  • Or a recipe and the dishes you cook from it.
  • Or a class and its objects.

Key facts

  • Images are immutable. To change one you build a new image (for example tag 1.1).
  • Each container adds its own thin writable layer on top of the image.
  • Deleting a container does not delete the image.

Docker architecture

When you type docker ... you are using a client that sends requests to a background service, the daemon, which does the real work.

Terminology cheat sheet

TermMeaning
Docker clientThe docker command you type. It sends API requests to the daemon.
Docker daemon (dockerd)Background service that builds images, manages containers, networks and volumes.
RegistryA server that stores and distributes images, for example Docker Hub or a private registry inside your organisation.
ImageRead-only template made of layers plus metadata (what to run, which user, and so on).
ContainerA running (or stopped) instance of an image.
TagA label for an image version, such as python:3.12-slim. The part before the colon is the repository name.

Build a Docker image

A Dockerfile is a text file of instructions. docker build follows them to produce an image.

Dockerfile

EXPOSE is documentation, not publishingEXPOSE 8000 only records that the application is intended to listen on port 8000. It does not make the port reachable from your computer. Publishing happens at run time with -p HOST_PORT:CONTAINER_PORT (or -P, which publishes all exposed ports to random host ports).
SituationReachable from the host?
EXPOSE 8000 in Dockerfile, run with no -pNo
No EXPOSE, run with -p 8080:8000Yes, at localhost:8080
EXPOSE 8000 and -p 8080:8000Yes, and the image documents its port

.dockerignore

Build context: what gets sent to Docker

When you run docker build ... ., the final . is the build context: the folder whose contents are sent to the daemon. COPY can only use files from this context. .dockerignore keeps unwanted files out of it.

Concept simulatorWhat is sent to the daemon?

Sizes are illustrative.

Image layers and the build cache

Each instruction that changes files adds a layer. Docker caches layers: if an instruction and everything it depends on are unchanged, the cached layer is reused. Once one layer changes, every layer after it is rebuilt. That is why the Dockerfile copies requirements.txt and installs packages before copying app.py.

Concept simulatorWhat does a rebuild redo?

    Build it

    Run in your real terminal
    docker build -t substation-monitor:1.0 .

    -t substation-monitor:1.0 names and tags the image. The final . is the build context. Run it from the folder that contains the Dockerfile.

    Choices that keep the image small and safe

    Small

    • python:3.12-slim instead of the full image
    • PIP_NO_CACHE_DIR=1 so pip's download cache is not stored
    • .dockerignore keeps junk out

    Safe

    • Pinned base tag and dependency versions
    • Runs as a non-root user (USER appuser)
    • No secrets in the Dockerfile or image

    Fast to rebuild

    • Rarely-changing steps first, frequently-changing steps last
    Expect a pip warningDuring the build, pip may print a warning about running as the root user. That is expected here because the install step runs before the USER instruction, and it only affects the build, not the final container.

      Environment variables

      An environment variable is a named setting handed to a process when it starts. They let one image behave differently in different places without rebuilding it. Set them with -e NAME=value, or many at once with --env-file.

      Modelled result

      Environment variables are not a vaultAnyone who can run docker inspect on the container can read its variables. For real secrets (passwords, API keys, tokens) use your platform's secret mechanism or a secrets manager. Just never bake them into the image.
      Run in your real terminal

      Security fundamentals

      Containers are not automatically secure. Four habits prevent the most common mistakes.

      1. Do not run as root without a reason

      If a process in the container is compromised, root inside the container has far more power to read, write and change things, especially with mounted volumes or extra privileges. Our Dockerfile creates appuser and switches to it with USER. Check with docker exec monitor whoami.

      2. Never hardcode secrets

      A password written into a Dockerfile or source file is stored in the image forever. Commands like docker history and docker inspect can reveal it, and every person who can pull the image gets it. Supply secrets at run time through a secrets mechanism, and rotate any that leaked.

      3. Control your image tags

      A tag such as latest is a moving label: tomorrow it can point to a different image than today. Pin versions (python:3.12-slim, or even a digest) so builds are repeatable and upgrades are deliberate.

      4. Do not use untrusted images

      An image can contain anything: crypto miners, backdoors, outdated vulnerable software. Prefer Docker Official Images and verified publishers, or images from your organisation's own registry. Scan images for known vulnerabilities and review where an image came from.

      ExerciseSpot the risks

      This Dockerfile works, but it contains several security and quality problems. Click each risky line, then check your answers.

      Checklist before you share an image

      • Base image and dependency versions are pinned.
      • The final USER is not root.
      • No secrets, .env files, keys or .git folders are in the image (.dockerignore checked).
      • Only needed ports are published, and bound to 127.0.0.1 when only local access is required.
      • The image came from, and is stored in, a registry you trust.

      Step 6. Introduce a deliberate configuration error

      Remove the working container and start a new one without the SITE_NAME setting.

      Run in your real terminal
      docker rm -f monitor
docker run -d --name monitor -p 8080:8000 substation-monitor:1.0
docker ps
docker ps -a

      Expected: docker run still prints an ID, but docker ps does not list the container. docker ps -a shows STATUS like Exited (1) 3 seconds ago.

      Predict first: Why did docker run succeed yet the container is not running?

      Docker successfully created and started the container. Then the main process (our app) crashed immediately, so the container exited. A container lives only as long as its main process.

      Step 7. Diagnose and fix it

      Run in your real terminal
      docker logs monitor
docker inspect -f "{{.State.ExitCode}}" monitor
docker rm monitor
docker run -d --name monitor -p 8080:8000 -e SITE_NAME=GETRI-Lab substation-monitor:1.0
docker ps

      Expected: the logs end with KeyError: 'SITE_NAME'; the exit code is 1. After recreating with -e the container shows as "Up" again and /health responds.

      Bonus challenge: Break and fix the port mapping

      Run a container with -p 8080:8001 (wrong container port). The container is "Up", but curl to localhost:8080 fails. Use docker ps and docker logs to find the mismatch, then recreate it with -p 8080:8000.

      Bonus challenge: Reproduce the localhost-binding error without rebuilding

      Run docker rm -f monitor, then docker run -d --name monitor -p 8080:8000 -e SITE_NAME=GETRI-Lab substation-monitor:1.0 uvicorn app:app --host 127.0.0.1 --port 8000. The container is "Up", yet curl localhost:8080/health fails. Find the clue in docker logs, then recreate it without the extra command.

      Step 8. Clean up

      Run in your real terminal
      docker stop monitor
docker rm monitor
docker ps -a
docker rmi substation-monitor:1.0

      docker rmi deletes the image. You can skip it if you want to keep it for practice.
