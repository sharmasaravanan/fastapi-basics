DevOps Explained: From Code to Production

How does a piece of software travel from a developer's keyboard to a system that people rely on every day — and how can that journey be fast, safe and repeatable? This module explains it step by step, in plain English, using an example from the power sector.

By the end you will understand

  • How software moves from development to production (the live system people use).
  • Why DevOps exists and which problems it solves.
  • How a monolith differs from microservices.
  • Where Docker, automated delivery, orchestration and monitoring fit in the complete workflow.

Our running analogy. Releasing software is like bringing a new component into service at a substation: it is designed, checked against a standard test list, packaged, installed by an approved procedure, watched after energising, and the lessons are fed back into the next job. DevOps is the discipline of making that cycle smooth and repeatable for software.
About the example in this module. The “Power Operations Monitoring System” is a fictional teaching application. It uses simulated data only and is not connected to any real power infrastructure.

The journey (click any step to jump)

    1 Why DevOps exists

    Before we meet any tool, let us look at the people and the problem. Software is a set of instructions that tells computers what to do. Four groups of people usually touch it before it reaches users:

    • Developers write the software.
    • Testers check that it works and is safe to release.
    • Infrastructure team prepares the servers (the computers that run software for many users).
    • Operations team keeps the live system running day and night.

    The traditional handoff. Each group finished its part and “threw it over the wall” to the next, often by email, tickets or a long document. Click a box below, then press the button to watch one small change travel through this old process.

    Five common problems (expand each)

    “It works on my machine”

    What it means: The program runs perfectly on the developer's laptop but fails on the test or production computer.

    Why: The two computers differ — for example a different version of the Python language, a missing add-on library (a dependency) or a different setting.

    How DevOps helps: The application is packaged together with what it needs (a container), so it behaves the same everywhere.

    Inconsistent environments

    What it means: An environment is a place where software runs: a developer laptop, a test area, a rehearsal area, or the live system. If each was built by hand, no two are identical.

    Example: Testing passes in the test area, but the live system has an older database version, so a feature breaks only after release.

    How DevOps helps: Environments are described in files and created the same way every time.

    Manual deployments

    What it means: Deployment is putting a new version into an environment. Done manually, someone follows a 40-step document at night, copying files and typing commands.

    Example: Step 27 is skipped because the person was interrupted. Nobody notices until users complain.

    How DevOps helps: A pipeline performs the same steps automatically, every time.

    Configuration mistakes

    What it means: A configuration is a group of settings, such as the address of a database. One typing error or forgotten setting can stop the system.

    Example: The test database address is accidentally left in the live system.

    How DevOps helps: Settings are kept as reviewed files under version control instead of being typed by hand.

    Slow incident recovery

    What it means: An incident is an unplanned problem in the live system. Recovery is slow when nobody knows what changed, who can fix it, or how to go back.

    Example: At 2 a.m. the application is down; the developer who knows it is unreachable.

    How DevOps helps: Monitoring shows what is wrong, every change is recorded, and a rollback to the previous working version is quick.

    So what is DevOps?

    DevOps (“Development” plus “Operations”) is a way of working in which the people who build software and the people who run it share responsibility for it from idea to daily operation, and use automation to make releases small, frequent and safe.

    It has three parts: people and culture (shared goals, no blame), process (small changes, regular feedback) and tools (automation). It is not a product you can buy, and not a job title for one person.

    Why it matters

    Slow, error-prone releases cost time and cause outages. Shared responsibility and automation shorten delivery and make it more reliable.

    How it works

    Teams work together, release small changes, automate repeatable steps, and watch the live system to learn quickly.

    Example

    A report layout change goes live in hours, with automatic checks and a quick undo, instead of waiting for a monthly release night.

    Common mistake

    Buying tools but leaving teams working separately. Tools without shared responsibility just automate the old handoffs.

    3 Monolithic architecture versus microservices
    
      
    Architecture means how an application is divided into parts. There are two broad styles. A
        monolith is built and deployed as one single unit. Microservices split the application into small services, each doing
        one job and deployed separately. Click any part of the diagram, then try the buttons.
    
      
    
        
        
        
      
    
      
    
        
      
    
      
    Click any box in the diagram for an explanation.
    
      
    Use the buttons above to compare what happens in each style.
    

      
    Comparing the two styles
    
      
    
        
    
          
            
    
              Question
              Monolith
              Microservices
            
    
              
          
            
    
              Deployment
              One package is deployed. Simple, but every change means redeploying everything.
              Each service is deployed separately. More pieces to deploy, but a small change touches a small piece.
              
            
    
            
    
              Scaling (handling more load)
              You run more copies of the whole application, even if only one part is busy.
              You add copies of only the busy service.
            
    
            
    
              Independent changes
              Teams share one code base and one release schedule; changes can collide.
              Teams can change and release their own service on their own schedule, if agreements between services
                are kept.
            
    
            
    
              Network communication
              Parts call each other inside one program: fast and reliable.
              Services call each other over the network: slower, and calls can fail or time out, so extra care is
                needed.
            
    
            
    
              Complexity
              Simpler to understand and test at first; can become tangled as it grows.
              Each service is simple, but the whole system is more complex (many moving parts, data spread
                out).
            
    
            
    
              Operational overhead
              Low: one thing to deploy, monitor and back up.
              High: many things to deploy, monitor, secure and troubleshoot; usually needs automation and
                orchestration.
            
    
              
        
    
      
    
      
    
        
    When a monolith is a sensible choice
          
      
            
    • A small team and a fairly simple application.
      • 
            
    • The requirements are still changing and speed of learning matters.
      • 
            
    • Few users, so scaling parts separately is not needed.
      • 
            
    • The team has limited experience running many services.
      • 
          
    
        
    
        
    When microservices can help
          
      
            
    • Several teams need to release independently.
      • 
            
    • Some parts have very different load or reliability needs.
      • 
            
    • The application is large and a single package has become hard to change.
      • 
            
    • The organisation can support the extra automation and monitoring.
      • 
          
    
        
    
      
    
      
    Microservices are not “better”; they are a trade-off. They
        solve some problems of large systems and create others. Many successful systems are well-organised monoliths,
        and many organisations start there.
    
      
    
        
    
          
    Why it matters
    
          
    The architecture you choose decides how you build, release, scale and operate the system for years.
    
        
    
        
    
          
    How it works
    
          
    Monolith: one package with internal calls. Microservices: separate services that cooperate through network
            requests.
    
        
    
        
    
          
    Example
    
          
    POMS could start as a monolith. If the reporting part grows and needs its own team, it could be separated
            into a reporting service later.
    
        
    
        
    
          
    Common mistake
    
          
    Splitting a small application into many services “because it is modern”, and then spending more
            time on the plumbing than on the features.
    
        
    
      
    
    
    

    
    
    
      
    4 The end-to-end DevOps workflow
    
      
    Here is the complete journey of one change to POMS. A pipeline is a
        fixed series of automatic steps a change must pass. Click any stage, or press Play to watch the
        change travel from the developer to the running system and back again as feedback.
    
      
    
        
        
        
      
    
      
    
      
    

      
    
        
    
          
    Why it matters
    
          
    Every manual step is a chance for error. A pipeline makes the route from code to production the same every
            time.
    
        
    
        
    
          
    How it works
    
          
    Code is stored and checked, tested automatically, packaged into a container image, stored in a registry,
            deployed, kept running, and watched.
    
        
    
        
    
          
    Example
    
          
    A developer changes the alert threshold for transformer temperature. Within minutes the pipeline has tested
            and packaged it, ready for release.
    
        
    
        
    
          
    Common mistake
    
          
    Skipping stages “just this once” under deadline pressure. The urgent fixes are exactly the ones
            that most need the checks.

    The DevOps feedback loop

        planning. Click a stage, or let the loop trace one improvement.
    
      
    
      
    
      
    Click any stage in the loop.
    
      
    
        
    
          
    Why it matters
    
          
    Release speed is only useful if quality stays high. Feedback is how teams catch problems early and improve
            with every release.
    
        
    
        
    
          
    How it works
    
          
    Small changes flow through the pipeline; monitoring and users report what happened; the team turns the

    Common mistake
    
          
    Treating “deployed” as “done”. The loop only closes when someone looks at the
            results and acts.
    
        
    
      
    
    
    

    
    
    
      
    5 The technology stack, explained
    
      
    These are the tools you will hear about. Each solves one specific problem. The ones named here are widely used

    How the observation tools connect
    
      
    Once POMS is running, it produces two kinds of evidence: logs (written
        records of events) and metrics (numbers measured over time).
    
      
    
      
    
        
    
          
    Why it matters
    
          
    Knowing what each tool is for prevents both confusion and overspending on tools you do not need.
          
    
        
    
        
    
          
    How it works
    
          
    Tools line up along the journey: write → store → test → package → run → observe.
            Each hands its result to the next.
    
        
    
        
    
          
    Example

            Grafana shows if it is healthy.
    
        
    
        
    
          
    Common mistake
    
          
    Adopting a tool because others do. Start from the problem you have, then pick the simplest tool that solves
            it.
    
        
    
      
    
    
    

    
    
    
      
    6 Virtual machines versus containers
    
      
    Both let several applications share one physical computer without interfering with each other. They do it in
        different ways. First, some words. The operating system (OS) is the main
        software of a computer, such as Windows or Linux. Its core, the kernel, controls hardware and running programs. Isolation means
        keeping programs separated so that a problem in one does not spread to another.
    
      
    
      
    Simplified: some virtual-machine set-ups also include a host operating system beneath the
          hypervisor.

              Aspect
              Virtual machine
              Container
            
    
              
          
            
    
              What it contains
              A full guest operating system plus libraries plus the application.
              The application plus its libraries; it uses the host's kernel.
            
    
            
    
              Isolation
              Strong: separate operating systems.
              Good: separated by the kernel, but all share one kernel, so the host must be kept secure and up to
                date.
            
    
            
    
              Size and speed
              Larger (gigabytes); typically takes minutes to start.
              Smaller (often megabytes); typically starts in seconds.
            
    
            
    
              Different operating systems
              Yes: a Windows VM and a Linux VM can run side by side.
              Containers share the host's kernel, so they follow the host's operating-system family.
            
    
            
    
              Typical use
              Legacy applications, strict separation, whole-server environments.
              Packaging and running modern applications consistently.
            
    
              
        
    
      
    
      
    Not either/or. Many organisations run containers inside
        virtual machines: the VM gives strong separation between teams, and containers give light, consistent packaging.
      
    
      
    
        
    
          
    Why it matters
    
          
    Lighter packaging means faster releases, quicker recovery and fewer servers for the same workload.
    
        
    
        
    
          
    How it works
    
          
    A VM virtualises hardware and carries its own operating system. A container virtualises at the
            operating-system level and shares the host kernel.
    
        
    
        
    
          
    Example
    
          
    POMS's readings, alerts and report parts can run as three small containers on one server, rather than three
            full virtual machines.
    
        
    
        
    
          
    Common mistake
    
          
    Believing containers are “tiny virtual machines” with equal isolation. They are lighter
            precisely because they share more.
    
        
    
      
    
    
    

    
    
    
      
    7 Containers versus orchestration
    
      
    A container is a sealed, lightweight box holding one application
        and what it needs. Three tools appear here, each with a different scope. Their jobs overlap a little, but they
        are not the same.
    
      
    
      
    
      
    Try the buttons to see how the orchestrator reacts (the Kubernetes
        panel above).
    

      
    
        
    
          
            
    
              Question
              Docker
              Docker Compose
              Kubernetes
            
    
              
          
            
    
              Main job
              Build container images and run containers.
              Describe and run several related containers together.
              Run and manage containers across a group of computers.
            
    
            
    
              Scope
              One container, one computer.
              A small application, one computer.
              Many applications, many computers (a cluster).
            
    
            
    
              If a container crashes
              Can be restarted on the same computer if you set that option.
              Same: can restart on the same computer.
              Detects and replaces it automatically, on any suitable computer.
            
    
            
    
              If the computer fails
              Everything on it is down until a person acts.
              Same.
              Starts replacements on other computers.
            
    
            
    
              Scaling
              Manual.
              Limited, on one computer.
              Adds or removes copies automatically or on request.
            
    
            
    
              Effort to learn and run
              Low.
              Low.
              Higher; usually needs a dedicated platform team or a managed service.
            
    
              
        
    
      
    
      
    Overlap, not replacement. Docker (and compatible tools) create the
        container images; Kubernetes runs those standard container images at scale. Docker and Compose can restart a
        crashed container, and Compose can run several containers, so the responsibilities overlap — but only an
        orchestrator coordinates a whole cluster. Do not choose Kubernetes for a small application that
        fits comfortably on one server.
    
      
    
        
    
          
    Why it matters
    
          
    Choosing the right level avoids both under-engineering (manual recovery at 2 a.m.) and over-engineering (a
            complex cluster for one small tool).
    
        
    
        
    
          
    How it works
    
          
    You describe what you want (“run three copies of this image”). The tool makes it so, and keeps
            it so, within its scope.
    
        
    
        
    
          
    Example
    
          
    A training copy of POMS runs fine under Docker Compose. A busy shared version for many sites may justify
            Kubernetes.
    
        
    
        
    
          
    Common mistake
    
          
    Thinking Kubernetes replaces Docker, or that every project needs it. They solve different-sized problems.
